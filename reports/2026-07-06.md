# Claude Code ベストプラクティス調査レポート 2026-07-06

## 今週の新発見

### settings.json ― v2.1.175〜v2.1.200 の新規項目群

**発見内容**: 過去2週間で複数の新設定が追加された。特に非インタラクティブ・管理者運用向けの項目が充実している。

#### `availableModels` + `enforceAvailableModels`（v2.1.175+）

組織がユーザーに使用可能なモデルを限定できる。`enforceAvailableModels: true` を合わせて設定すると、デフォルトモデルもリスト内に強制される。

```json
// /etc/claude-code/managed-settings.json
{
  "availableModels": ["sonnet", "haiku"],
  "enforceAvailableModels": true
}
```

コスト管理・コンプライアンス目的でチームが Haiku / Sonnet のみ使用するよう制限したいケースに有効。

#### `askUserQuestionTimeout`（v2.1.200+）

`AskUserQuestion` ダイアログへの応答がなければ自動で続行させる設定。非インタラクティブ（Routines / CI）での詰まり防止に有効。

```json
// ~/.claude/settings.json
{
  "askUserQuestionTimeout": "5m"
}
```

受け入れ値: `"60s"` / `"5m"` / `"10m"` / `"never"`（デフォルト）。**ユーザースコープ専用**（project・local では無視）。

#### `disableSideloadFlags`（v2.1.193+）

`--plugin-dir`・`--plugin-url`・`--agents`・`--mcp-config` CLI フラグを起動時に拒否する。`strictKnownMarketplaces` ポリシーのバイパスを防止したいエンタープライズ向け。

```json
// managed-settings.json
{
  "disableSideloadFlags": true
}
```

#### `autoMode.classifyAllShell`（v2.1.193+）

`auto` モードでは通常、任意コード実行パターンのみ分類器を通すが、このフラグを立てると **全 Bash / PowerShell コマンド**が分類器を経由する。セキュリティを最優先にしたい CI 環境向け。

```json
{
  "autoMode": {
    "classifyAllShell": true
  }
}
```

#### `enableArtifact`（v2.1.196+）

Artifact ツールのユーザー単位の有効/無効化。Managed の `disableArtifact` が優先。

```json
// ~/.claude/settings.json
{
  "enableArtifact": false
}
```

#### `enabledMcpjsonServers`（v2.1.196+）

信頼されていないフォルダで `.mcp.json` 内のどのサーバーを承認するかをリストで指定。自動承認したいサーバーのみ絞り込める。

```json
// ~/.claude/settings.json
{
  "enabledMcpjsonServers": ["memory", "github", "filesystem"]
}
```

**適用提案**:
- Routines（スケジュール実行）で AskUserQuestion の詰まりを防ぐため `askUserQuestionTimeout: "5m"` を `~/.claude/settings.json` に追加する
- エンタープライズ管理者は `availableModels + enforceAvailableModels` でチームのモデル使用をコスト上限に合わせて制限する
- CI 環境の managed-settings.json に `autoMode.classifyAllShell: true` を追加して全シェルを安全審査下に置く

### マルチスラッシュコマンドスタック（v2.1.199）

**発見内容**: v2.1.199 以降、1回の入力で **複数のスラッシュコマンドを連続指定**できる。最初のスキルと最大5つの追加スキルがロードされ、末尾のテキストが各スキルへの引数として渡される。

```text
/code-review /fix-issue 1234
```

上の入力で `code-review` と `fix-issue` の両スキルが同時にロードされ、`1234` が引数として渡される。

#### 活用パターン例

```text
# レビューして修正まで一気に実行
/code-review /simplify

# 問題を調査してから修正
/security-review /fix-issue

# 最大6スキルのスタック
/review /test /lint /fix /commit /pr
```

**適用提案**:
- 日常的な「レビュー→修正」フローは `/code-review /simplify` の1入力で実行する
- CI 前のゲート処理として `/security-review /lint-check` を習慣化する

### CLAUDE.md ― 実効的命令予算モデルと削除テスト

**発見内容**: 公式ドキュメントと実測から、実効的な命令予算が明確化された。

#### 命令予算の構造

| リソース | 命令数 |
|---------|-------|
| Claude の組み込みシステムプロンプト | 約 50 命令 |
| フロンティア LLM の信頼できる上限 | 約 150〜200 命令 |
| **CLAUDE.md の実効予算** | **約 100〜150 命令** |

200行を超えると命令が「埋もれて」無視される確率が急増する（公式ドキュメント確認済み）。

#### 削除テスト（各行に適用）

> "Would removing this cause Claude to make mistakes?"（これを削除したら Claude が間違えるか？）

「No」なら削除。Claude がすでに正しくやっていることは CLAUDE.md に書かない。

#### CLAUDE.local.md ― 個人専用ファイルの活用

`.gitignore` に自動追加される `CLAUDE.local.md` は、共有したくない個人設定の置き場所。

```markdown
# CLAUDE.local.md（git 管理外）
- My personal shortcuts: use 'pnpm' not 'npm'
- My staging URL: https://staging-myname.example.com
- WIP: working on auth refactor in feature/auth-v2
```

| ファイル | 用途 |
|---------|------|
| `CLAUDE.md` | チーム共有の共通設定（git 管理） |
| `CLAUDE.local.md` | 個人ショートカット・WIP メモ・機密パス（git 管理外） |
| `~/.claude/CLAUDE.md` | 全プロジェクト共通のグローバル設定 |

**適用提案**:
- CLAUDE.md の各行に削除テストを適用し、100 行以下を目指して整理する
- 個人の `pnpm` 設定・ステージング URL・WIP 作業メモは `CLAUDE.local.md` に移動する

### MCP ― ゲートウェイパターンと推奨スターターセット

**発見内容**: MCP サーバーを 10 以上使う場合の新アーキテクチャパターンと、2026 年時点の推奨スターターセットが明確化された。

#### MCPゲートウェイパターン（10+ サーバー向け）

```
Claude Code
    │
    └── MCP Gateway（1エンドポイント）
            ├── GitHub Server
            ├── Linear Server
            ├── Slack Server
            ├── Database Server
            └── ... (選択的ロード)
```

ゲートウェイがツール検索・選択的ロードを担当することで、Claude が受け取るツールリストを常に最小限に保てる。

#### 2026 年推奨スターターサーバー（5本セット）

| サーバー | 役割 |
|---------|------|
| `filesystem` | ローカルファイル操作 |
| `github` | PR・Issue・コメント操作 |
| `context7` | ライブラリの最新ドキュメントを取得（学習データ汚染回避） |
| `playwright` | ブラウザ自動操作・スクリーンショット |
| `sequential-thinking` | マルチステップ推論の精度向上 |

#### MCP スコープ設計ルール

```
~/.claude/settings.json  → 全プロジェクト共通（GitHub, Slack 等）
.claude/settings.json    → プロジェクト固有（DB, API 等）
.mcp.json                → チーム共有（git 管理）
```

`enabledMcpjsonServers` で `.mcp.json` 内の自動承認サーバーをリスト管理することで、信頼されていないフォルダでも安全に使用できる。

**適用提案**:
- `context7` を `~/.claude/settings.json` に追加して、すべてのプロジェクトでライブラリの最新ドキュメントを参照できるようにする
- 10 を超えるサーバーを使う場合は MCP ゲートウェイの導入を検討し、Claude が受け取るツール数を 40 以下に抑える
- `sequential-thinking` サーバーを追加してマルチステップタスクの品質を向上させる

### ワークフロー ― Writer/Reviewer パターンの公式化と並列ファンアウト

**発見内容**: 公式ドキュメントで Writer/Reviewer パターンが正式に説明された。また大規模マイグレーション向けのファンアウトスクリプトパターンも整備された。

#### Writer/Reviewer パターン（2セッション並列）

| Session A（Writer） | Session B（Reviewer） |
|--------------------|-----------------------|
| `Implement a rate limiter for our API endpoints` | — |
| — | `Review @src/middleware/rateLimiter.ts for edge cases, race conditions, and consistency with existing middleware` |
| `Here's the feedback: [Session B output]. Address these issues.` | — |

Session B はフレッシュコンテキストで実行するため、自分が書いたコードへのバイアスがなく、厳密なレビューが可能。

テストでも同様のパターンが有効：Session A がテストを書き、Session B がそのテストをパスするコードを実装する（TDD の並列化）。

#### 大規模ファンアウトスクリプト

```bash
# 大量ファイルの並列マイグレーション例
for file in $(cat files.txt); do
  claude -p "Migrate $file from React to Vue. Return OK or FAIL." \
    --allowedTools "Edit,Bash(git commit *)" \
    --output-format json
done

# 並列実行（最大8プロセス）
cat files.txt | xargs -P 8 -I{} \
  claude -p "Migrate {} from React to Vue." \
  --allowedTools "Edit,Bash(git commit *)"
```

`--allowedTools` で権限を最小化することで、無人実行時の安全性を確保する。

#### ターゲットコンパクションの活用

```bash
# 特定の情報を保持しながらコンパクション
/compact Focus on the API authentication changes and test failures

# API 変更に関する情報だけを保持してコンテキストを圧縮
```

**適用提案**:
- 大型機能実装後は別ターミナルで Session B（Reviewer）を立ち上げ、フレッシュコンテキストでレビューする習慣をつける
- 大量ファイルマイグレーションでは `xargs -P 8` で並列ファンアウトし、`--allowedTools` で権限スコープを最小化する
- 長時間セッション中は定期的に `/compact Focus on [現在のタスクの焦点]` を実行し、不要な情報を圧縮する

### プロンプト設計 ― 公式の Before/After パターン集

**発見内容**: 公式ドキュメントで効果的なプロンプトの Before/After パターンが整備された。

| 戦略 | Before（悪い例） | After（良い例） |
|------|-----------------|----------------|
| タスクをスコープする | `"add tests for foo.py"` | `"write a test for foo.py covering the case where the user is logged out. avoid mocks."` |
| 出典を指示する | `"why does ExecutionFactory have a weird api?"` | `"look through ExecutionFactory's git history and summarize how its api came to be"` |
| 既存パターンを参照する | `"add a calendar widget"` | `"look at HotDogWidget.php to understand patterns. implement a calendar widget without new libraries."` |
| 症状を説明する | `"fix the login bug"` | `"users report login fails after session timeout. check src/auth/, especially token refresh. write a failing test that reproduces it, then fix it."` |

**適用提案**:
- プロンプトには必ず「どのファイル」「どの条件」「完了条件」の3要素を含める
- バグ修正では「現象 → 調査範囲 → 再現テスト → 修正」の順序をプロンプトに明示する
