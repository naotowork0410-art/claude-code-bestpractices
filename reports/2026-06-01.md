# Claude Code ベスプラ調査レポート 2026-06-01

## 今週の新発見

### AutoDream ― セッション間メモリを自動統合するバックグラウンドサブエージェント

**発見内容**: Q1 2026 に実装された `AutoDream` は、セッション終了後に起動するバックグラウンドサブエージェントで、`~/.claude/projects/<project>/memory/` 配下のメモリファイルを自動的に整理・統合する。

#### AutoDream の動作

- セッション終了をトリガーに起動（ユーザー操作不要）
- 複数セッションにわたって記録された同一の知見（例: デプロイ手順の注意点）を1エントリに統合
- 矛盾する記録がある場合は最新のものを優先してマージ
- 結果は `MEMORY.md`（インデックス）とトピック別ファイルに保存

#### 有効/無効の切り替え

```json
// ~/.claude/settings.json
{
  "autoDreamEnabled": true  // デフォルト: true（プロで有効）
}
```

#### 稼働確認

```bash
# セッション内で実行
/memory
# → "Auto-dream: on" と表示されれば稼働中
```

**適用提案**:
- デフォルト有効のため基本的に何もしなくてよい。無効化したい場合は `autoDreamEnabled: false` を設定
- `/memory` コマンドで定期的にインデックスを確認し、不要なエントリを手動削除してノイズを抑制
- `autoMemoryDirectory` で保存先をカスタマイズ可能（デフォルト: `~/.claude/projects/<project>/memory/`）

### `.claudeignore` ― コンテキスト使用量を最大 70% 削減するファイル除外設定

**発見内容**: プロジェクトルートに `.claudeignore` を配置すると、Claude の自動ファイル探索（検索・インデックス）から指定パターンのファイルを除外できる。`.gitignore` と同じ構文で、プロジェクトに 500 ファイル超のコードがある場合にコンテキスト削減の最大レバレッジになる。

#### 設定例

```gitignore
# .claudeignore
node_modules/
dist/
build/
coverage/
__pycache__/
*.lock
*.log
.next/
vendor/
```

#### `.claudeignore` vs `permissions.deny` の使い分け

| 機能 | 効果 | 用途 |
|------|------|------|
| `.claudeignore` | 自動探索のみブロック。明示的パス指定では読める | 依存関係・ビルド出力など「関係ないが機密でない」ファイル |
| `permissions.deny` | 読み取り自体をブロック（明示的パス指定でも不可） | `.env`・秘密鍵など機密ファイル |

> "A well-configured ignore file can cut per-request context by 40-70% depending on what you exclude."

**適用提案**:
- `node_modules/`, `dist/`, `build/`, `coverage/`, `__pycache__/` を最低限除外
- `*.lock` ファイルも除外対象（大きくて Claude には不要）
- 機密ファイルは `.claudeignore` ではなく `permissions.deny` に設定する

### `/goal` コマンド ― 複数ターンにわたる自律完了条件の設定（v2.1.139）

**発見内容**: 2026年5月12日リリースの v2.1.139 で `/goal` コマンドが追加された。完了条件をテキストで定義すると、Claude が条件を満たすまで自律的に計画・実装・テスト・リファクタリングを繰り返す。長時間の無人実行（数時間〜数日）が可能になった。

#### 使い方

```text
# セッション内で実行
/goal すべての lint エラーが 0 件、テストカバレッジが 90% 以上、ビルドが成功

# または自然言語プロンプトに組み込む
/goal 以下の条件をすべて満たしたら停止:
  1. `npm test` がすべてパス
  2. `npm run lint` がエラーゼロ
  3. `npm run build` が成功
```

#### `/goal` の内部動作

```
[Claude 実装] → [evaluator サブエージェントが条件チェック] → [未達なら次ターン] → ...
                                                              → [達成なら停止]
```

- 条件評価は毎ターン後に **evaluator サブエージェント**（別コンテキスト）が行う
- Stop フックと組み合わせると「スクリプトが pass を返すまで停止させない」も可能
- 公式ドキュメントでは「8 連続ブロック後は Claude Code が強制終了」と明記

#### Stop フックとの組み合わせ

```json
// .claude/settings.json
{
  "hooks": {
    "Stop": [{
      "type": "command",
      "command": "npm test && npm run lint && npm run build && echo 'OK' || exit 2"
    }]
  }
}
```

`exit 2` でターンをブロック → Claude がエラーを読んで修正 → 再チェック、というループが自動化される。

**適用提案**:
- 長時間かかるリファクタリング・マイグレーション作業に `/goal` を使う（その間他の作業が可能）
- 条件は「スクリプトで検証可能」なものに限定する（曖昧な条件は無限ループのリスク）
- Stop フック + `/goal` の組み合わせで最も信頼性の高い自律ループが構築できる

### `sandbox` 詳細設定 ― ファイルシステム・ネットワーク分離の完全制御

**発見内容**: `settings.json` の `sandbox` オブジェクトが大幅に拡充され、ファイルシステムとネットワークを細粒度で制御できるようになった。OS レベル（Linux: bubblewrap / macOS: seatbelt）で分離が実施される。

#### 設定例（プロジェクト用）

```json
{
  "sandbox": {
    "enabled": true,
    "failIfUnavailable": true,
    "autoAllowBashIfSandboxed": true,
    "filesystem": {
      "allowWrite": ["/tmp/build", "~/.kube"],
      "denyWrite": ["/etc", "/usr/local/bin"],
      "denyRead": ["~/.aws/credentials", "./.env"],
      "allowRead": ["."],
      "allowManagedReadPathsOnly": false
    },
    "network": {
      "allowedDomains": ["*.npmjs.org", "api.github.com"],
      "allowUnixSockets": ["~/.ssh/agent-socket"],
      "allowLocalBinding": true
    }
  }
}
```

#### 各フィールドの使い分け

| フィールド | 説明 |
|-----------|------|
| `failIfUnavailable` | sandbox が使えない OS では起動失敗（安全側に倒す） |
| `autoAllowBashIfSandboxed` | sandbox 内では Bash の都度確認をスキップ |
| `excludedCommands` | sandbox の対象外にするコマンドパターン（例: `docker *`） |
| `filesystem.allowManagedReadPathsOnly` | 管理者が許可したパスのみ読み取り可（Enterprise向け） |
| `network.allowedDomains` | 接続を許可するドメインのホワイトリスト |

**適用提案**:
- CI/CD 環境では `sandbox.enabled: true` + `failIfUnavailable: true` を強制する
- `denyRead: ["~/.aws/credentials", "./.env"]` を全プロジェクトの共通設定として `~/.claude/settings.json` に追加
- `network.allowedDomains` でアクセス可能な外部 API を限定し、情報漏洩リスクを削減

### `settings.json` 新設定項目まとめ ― worktree / attribution / スキルコスト最適化

**発見内容**: v2.1.90〜v2.1.139 にかけて実用的な新設定が多数追加された。これまでの調査で未カバーのものを整理する。

#### worktree 設定

```json
{
  "worktree": {
    "baseRef": "main",
    "symlinkDirectories": ["node_modules", ".cache"],
    "sparsePaths": ["packages/my-app", "shared/utils"],
    "bgIsolation": "worktree"
  }
}
```

| フィールド | 説明 |
|-----------|------|
| `baseRef` | ワークツリーの基準ブランチ |
| `symlinkDirectories` | コピーせずシンボリックリンクで共有するディレクトリ（`node_modules` はここに） |
| `sparsePaths` | 大規模モノレポで必要なパスだけチェックアウト |
| `bgIsolation` | バックグラウンドセッションの分離方式 |

#### attribution / prUrlTemplate

```json
{
  "attribution": {
    "commit": "🤖 Generated with Claude Code",
    "pr": false
  },
  "prUrlTemplate": "https://reviews.example.com/{owner}/{repo}/pull/{number}"
}
```

- `attribution.commit` でコミットメッセージ末尾の帰属表示をカスタマイズ（`false` で無効化）
- `prUrlTemplate` で社内 PR レビューツールへのリダイレクト URL を設定

#### スキルコスト最適化

```json
{
  "skillListingBudgetFraction": 0.01,
  "maxSkillDescriptionChars": 512
}
```

| フィールド | 説明 | デフォルト |
|-----------|------|---------|
| `skillListingBudgetFraction` | スキル一覧表示に使うコンテキスト比率 | `0.01`（1%） |
| `maxSkillDescriptionChars` | スキル説明文の最大文字数（超過分は切り捨て） | `1536` |

スキル数が多くなってきたら `maxSkillDescriptionChars: 512` に下げるとセッション開始時のコンテキスト消費を削減できる。

#### その他の新設定

```json
{
  "alwaysThinkingEnabled": true,
  "allowedHttpHookUrls": ["https://hooks.example.com/*"],
  "fileCheckpointingEnabled": true,
  "autoScrollEnabled": false,
  "spinnerTipsEnabled": false,
  "outputStyle": "Explanatory"
}
```

| フィールド | 説明 |
|-----------|------|
| `alwaysThinkingEnabled` | セッション全体で拡張思考（Extended Thinking）を常時有効 |
| `allowedHttpHookUrls` | HTTP フックが接続できる URL のホワイトリスト（セキュリティ必須） |
| `fileCheckpointingEnabled` | 編集前にファイルスナップショットを作成（デフォルト `true`） |
| `autoScrollEnabled` | 出力を自動スクロールで追う（`false` で固定） |
| `spinnerTipsEnabled` | 処理中のヒント表示を制御 |
| `outputStyle` | Claude の応答トーンを調整（"Explanatory" で詳細説明モード） |

**適用提案**:
- 並列ワークツリー利用者は `worktree.symlinkDirectories: ["node_modules"]` で初期化時間を大幅短縮
- HTTP フックを使う場合は必ず `allowedHttpHookUrls` でエンドポイントを明示的に限定する
- チームで Claude Code を使う場合は `attribution.commit` を統一してコミット履歴を整理

### 1M トークンコンテキストと戦略の変化

**発見内容**: 2026年3月より Opus 4.6 / Sonnet 4.6 では最大 **100万トークン**のコンテキストウィンドウが追加料金なしで利用可能になった。しかし「コンテキストが広いほど良い」ではなく、戦略の変化が必要。

#### コンテキスト量とパフォーマンスの関係（2026年版）

| 状況 | 推奨戦略 |
|------|---------|
| 小規模タスク（< 10K トークン） | `/clear` を積極利用してノイズを最小化 |
| 中規模（10K〜100K） | `.claudeignore` + `skills` でコンテキストの質を高める |
| 大規模（100K〜1M） | サブエージェントに委譲してメインセッションはシンプルに保つ |

> "Even with 1M tokens, context management still matters because more context doesn't mean better output — it means more noise for Claude to sift through."

1M トークンで「全ファイルを読み込む」アプローチはかえって性能を下げる。**コンテキストの量より質**が依然として重要。

#### 新しいコンテキスト最適化優先順位

1. `.claudeignore` で不要ファイルの自動探索を阻止（最高 ROI）
2. `maxSkillDescriptionChars: 512` でスキル一覧のコスト圧縮
3. `autoMemoryEnabled` + AutoDream でセッション間の知識を蓄積・圧縮
4. サブエージェントに調査を委譲（メインセッションに読み込んだファイルが残らない）
5. `/compact <instructions>` で圧縮時の保持内容を制御

**適用提案**:
- まず `.claudeignore` を作成し、`node_modules/`, `dist/`, `build/`, `*.lock` を除外する
- 1M トークンは「長時間セッション」ではなく「大規模ファンアウト」に活用する（並列サブエージェント）

- [ ] **`.claudeignore` をプロジェクトルートに作成**: `node_modules/`, `dist/`, `build/`, `coverage/`, `__pycache__/`, `*.lock` を最低限除外。コンテキスト 40-70% 削減が期待できる
- [ ] **`autoDreamEnabled: true` を確認**: `/memory` コマンドで "Auto-dream: on" を確認。メモリが肥大化している場合は不要エントリを手動削除

- [ ] **長時間タスクに `/goal` を活用**: 「テスト全パス・lint エラーゼロ・ビルド成功」を条件に設定し、その間他の作業を並行する
- [ ] **`worktree.symlinkDirectories: ["node_modules"]` を設定**: 並列セッションでの `node_modules` コピー時間を排除
- [ ] **`attribution.commit` をチームで統一**: デフォルトの attribution 文言を確認・カスタマイズ（またはプロジェクト方針に従い `false` に設定）
- [ ] **`maxSkillDescriptionChars: 512` を試験導入**: スキル数が 10 以上ある場合、セッション開始時のコンテキスト消費を削減できる
- [ ] **HTTP フックを使用中なら `allowedHttpHookUrls` を設定**: セキュリティのため接続先 URL を明示的にホワイトリスト化
- [ ] **`alwaysThinkingEnabled: true` を高精度が必要なプロジェクトに設定**: Extended Thinking を常時有効にして推論品質を向上
