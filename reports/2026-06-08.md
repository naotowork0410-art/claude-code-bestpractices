### Skills とカスタムコマンドの統合 ― `.claude/skills/` への完全移行

**発見内容**: 公式ドキュメントが確認。従来の `.claude/commands/<name>.md` と `.claude/skills/<name>/SKILL.md` は**同等に機能**し、どちらも `/<name>` で起動できる。ただし Skills は追加機能（サポートファイルディレクトリ、詳細フロントマター、モデル切替、サブエージェント実行）を持つため、新規作成はすべて `.claude/skills/` 形式が推奨。

#### Skills フロントマターの全フィールド（2026年6月時点）

```yaml
---
name: deploy-staging
description: Deploy the app to staging. Use when asked to deploy or push to staging.
when_to_use: "user says 'deploy', 'push to staging', 'release'"
argument-hint: "[branch-name]"
arguments: [branch]
disable-model-invocation: true  # 副作用あり：手動起動のみ
user-invocable: true            # / メニューに表示
allowed-tools: Bash Read        # このスキル実行中に許可するツール
disallowed-tools: AskUserQuestion  # 自律実行中は人への問いかけを禁止
model: sonnet                   # このスキルのみ適用するモデル
effort: high                    # 推論コスト：low/medium/high/xhigh/max
context: fork                   # サブエージェントとして実行
paths:
  - "src/**/*.ts"               # このパターンのファイルを扱う時のみ自動適用
---
```

#### 動的コンテキスト注入（Shell Injection）

SKILL.md 内でバッククォート付き `!` プレフィックスを使うと、スキル実行時にシェルコマンドの出力をインライン展開できる。

```markdown
---
description: Summarize uncommitted git changes
---

## Current diff
!`git diff HEAD`

## Instructions
Summarize the changes above in 2-3 bullets, flag any risks.
```

この仕組みにより、スキルがコンテキストを消費するのは**実際に使われる時だけ**（CLAUDE.md に書いた場合は毎セッションコストがかかる）。

**適用提案**:
- 「CLAUDE.md に手順が増えてきた」「同じ指示を3回以上貼った」→ `.claude/skills/` に移行
- 副作用のある操作（デプロイ・コミット・DB変更）は `disable-model-invocation: true` を必ず付ける
- `context: fork` でサブエージェント実行にすると、スキル実行がメインセッションのコンテキストを汚染しない
- `allowed-tools` でスキル実行時の権限を最小化する
- `~/.claude/skills/` に置けば全プロジェクト共通で使える

### CLAUDE.md ― `.claude/rules/` によるパス別ルール分離

**発見内容**: 公式ドキュメントで CLAUDE.md の **200行ガイドライン** と `.claude/rules/` によるモジュール分割が正式に推奨された。パス指定（`paths` フロントマター）で特定ファイルを扱う時のみルールをロードできるため、CLAUDE.md の肥大化を構造的に解決できる。

#### `.claude/rules/` の構造例

```
.claude/
├── CLAUDE.md              # 全セッション共通（200行以内）
└── rules/
    ├── code-style.md      # コードスタイル（常時ロード）
    ├── testing.md         # テスト規約（常時ロード）
    └── api-rules.md       # API設計（src/api/ 読み込み時のみ）
```

`api-rules.md` にパス指定フロントマターを追加:

```markdown
---
paths:
  - "src/api/**/*.ts"
  - "src/api/**/*.js"
---

# API 設計規約
- エンドポイントには必ず入力バリデーションを実装
- エラーは標準フォーマット `{ error: string, code: string }` で返す
- リストエンドポイントにはページネーションを含める
```

#### HTML コメントでトークンを節約

CLAUDE.md 内のブロックレベル HTML コメント（`<!-- -->`）は Claude のコンテキストから除去される。メンテナー向けのメモをトークン消費なしで書ける。

```markdown
<!-- 2026-06: React 18 移行後に削除予定のレガシーパターンについての注記 -->
- レガシーコンポーネントは `src/legacy/` に隔離。新規作成しないこと
```

#### `claudeMdExcludes` でモノレポの不要 CLAUDE.md をスキップ

```json
// .claude/settings.local.json
{
  "claudeMdExcludes": [
    "**/other-team/.claude/rules/**",
    "**/vendor/**/CLAUDE.md"
  ]
}
```

#### `@import` で AGENTS.md と共存

他ツール（OpenAI Codex、Devin 等）と同一リポジトリを使う場合:

```markdown
<!-- CLAUDE.md -->
@AGENTS.md

## Claude Code 固有設定
- Plan Mode を src/billing/ 変更時は必ず使用
```

**適用提案**:
- 現在の CLAUDE.md が 200 行を超えているなら `.claude/rules/` に分割する
- フロントエンド・バックエンド・DB など領域別に `rules/` ファイルを作成し、`paths:` で対象を絞る
- メンテナー向けのコメントは `<!-- -->` で書いてトークン節約
- モノレポ環境では `.claude/settings.local.json` に `claudeMdExcludes` を設定

### MCP 設定 ― ツール数とコンテキスト消費の最適化

**発見内容**: MCP サーバーが増えるとコンテキスト消費が急増する問題が定量化された。10 サーバー・84 ツールで **15,540 トークン**がセッション開始時に消費された実測値がある。Tool Search 機能（Sonnet 4 / Opus 4 モデルで自動有効）により最大 85% 削減可能。

#### `.mcp.json` の推奨設定

```json
// プロジェクトルートの .mcp.json
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_TOKEN": "${GITHUB_TOKEN}"
      },
      "timeout": 30000
    },
    "database": {
      "command": "npx",
      "args": ["-y", "mcp-server-postgres"],
      "env": {
        "POSTGRES_URL": "${DATABASE_URL}"
      },
      "timeout": 60000
    }
  }
}
```

#### MCP 設定のベストプラクティス

1. **3〜5 サーバーに限定**: 10 サーバーを超える場合は MCP ゲートウェイを検討
2. **シークレットは環境変数展開**: `.mcp.json` に API キーを直書きしない（`${ENV_VAR}` 形式）
3. **タイムアウト設定**: `"timeout": 600000`（10分）を重い操作のサーバーに設定
4. **Tool Search の活用**: Sonnet 4 以上でセッション開始時のコンテキスト最大 85% 削減
5. **最小権限**: DB サーバーは読み取り専用ロールを推奨

**適用提案**:
- `.mcp.json` をプロジェクトルートに作成し、シークレットは `${ENV_VAR}` 形式で参照
- MCP サーバーは 5 個以内に抑え、超える場合はゲートウェイ集約を検討
- `settings.json` に `allowedMcpServers` でプロジェクト別に使えるサーバーを限定する

### カスタムスラッシュコマンド ― 実用的なワークフロー例

**発見内容**: `.claude/commands/` と `.claude/skills/` は統合されており、どちらも同じ形式で動作する。実際のチームで使われている高頻度コマンドパターンを確認した。

#### 実用的なコマンド例

**`/commit` ― コミットメッセージ自動生成**

```markdown
<!-- .claude/skills/commit/SKILL.md -->
---
description: Generate a descriptive commit message and commit staged changes
disable-model-invocation: true
allowed-tools: Bash
---

## 手順
1. `git diff --staged` でステージ済み変更を確認
2. 変更内容を分析し、Conventional Commits 形式でコミットメッセージを作成
   - `feat:` 新機能, `fix:` バグ修正, `refactor:` リファクタ, `docs:` ドキュメント
3. `git commit -m "<message>"` でコミット実行

$ARGUMENTS があれば追加コンテキストとして利用する。
```

**`/fix-issue` ― GitHub Issue の自動修正**

```markdown
<!-- .claude/skills/fix-issue/SKILL.md -->
---
description: Fix a GitHub issue end-to-end
argument-hint: "[issue-number]"
disable-model-invocation: true
---

GitHub Issue #$ARGUMENTS を修正する:

1. `gh issue view $ARGUMENTS` で Issue の詳細を取得
2. 問題の原因となるコードを特定
3. 修正を実装
4. テストを作成・実行（既存のテストもすべてパスすること）
5. `npm run lint` を実行してエラーがないことを確認
6. 修正内容の説明を含むコミットメッセージでコミット
7. `gh pr create` で PR を作成
```

**`/review-security` ― セキュリティレビュー**

```markdown
<!-- .claude/skills/review-security/SKILL.md -->
---
description: Review current diff for security vulnerabilities
context: fork
effort: high
---

現在の変更（`git diff HEAD`）をセキュリティ観点でレビュー:

!`git diff HEAD`

確認項目:
- SQL インジェクション / XSS / コマンドインジェクション
- 認証・認可の欠陥
- シークレット・認証情報のハードコード
- 安全でないデータ処理
- 依存関係の脆弱性

各問題について: ファイル名・行番号・重要度（High/Medium/Low）・修正提案を記載。
```

**適用提案**:
- 繰り返し使う手順を `.claude/skills/` に整理し、チームで `git` 管理する
- `disable-model-invocation: true` を副作用のあるコマンドに付ける
- `$ARGUMENTS` で引数を受け取るパターンで汎用性を高める
- セキュリティレビュー系は `context: fork` でサブエージェント実行にする

### サブエージェント活用 ― コンテキスト汚染を防ぐ設計

**発見内容**: 公式ドキュメントで「サブエージェントはコンテキスト管理の最強ツール」と明記された。メインセッションで大量ファイルを読み込む代わりに、サブエージェントに調査を委譲することでコンテキストをクリーンに保てる。

#### `.claude/agents/` によるカスタムサブエージェント定義

```markdown
<!-- .claude/agents/security-reviewer.md -->
---
name: security-reviewer
description: Reviews code for security vulnerabilities. Use when asked to review code for security issues.
tools: Read, Grep, Glob, Bash
model: opus
effort: high
---

あなたはシニアセキュリティエンジニアです。コードを以下の観点でレビューしてください:

- インジェクション脆弱性（SQL、XSS、コマンドインジェクション）
- 認証・認可の欠陥
- コード内のシークレット・認証情報
- 安全でないデータ処理

ファイルの具体的な行番号と修正提案を提示してください。
```

#### サブエージェントの利用パターン

```
# コードベース調査を委譲（メインセッションのコンテキストを消費しない）
Use subagents to investigate how our authentication system handles token refresh.

# 実装後の検証を別視点で
Use a subagent to review this implementation for edge cases and security issues.

# 並列調査
Use 3 subagents in parallel to investigate: 
  1. How we handle database transactions
  2. How we manage caching
  3. How we handle errors in the API layer
```

#### Writer/Reviewer パターン（バイアス排除）

```
# セッションA（Writer）
Implement a rate limiter for our API endpoints.

# セッションB（Reviewer）- 別セッション or サブエージェント
Review the rate limiter in @src/middleware/rateLimiter.ts.
Look for race conditions, edge cases, and consistency with existing patterns.
```

**適用提案**:
- 「20 ファイル以上を読み込む調査」はサブエージェントに委譲する
- `.claude/agents/` に専門特化エージェントを定義しておく（security-reviewer, performance-analyzer 等）
- 実装後は必ず別コンテキスト（サブエージェント）でレビューさせる（実装バイアスを排除）
- `memory: project` フロントマターでサブエージェントのセッション間知識を永続化

### コンテキスト管理 ― 4フェーズワークフローと /compact の使い分け

**発見内容**: 公式ベストプラクティスで 4 フェーズワークフロー（Explore → Plan → Implement → Commit）が体系化された。またコンテキスト管理コマンドの使い分けが整理された。

#### 4フェーズワークフロー

```
# フェーズ1: Explore（プランモードで探索）
[Plan Mode: Ctrl+Shift+P]
"Read /src/auth and understand how we handle sessions."

# フェーズ2: Plan（実装計画の作成）
[Plan Mode]
"I want to add Google OAuth. What files need to change? Create a plan."
# Ctrl+G でプランをエディタで直接編集可能

# フェーズ3: Implement（実装実行）
[通常モード]
"Implement the OAuth flow from your plan. Write tests and fix any failures."

# フェーズ4: Commit
"Commit with a descriptive message and open a PR."
```

#### コンテキスト管理コマンドの使い分け

| コマンド | 用途 | 使うタイミング |
|---------|------|-------------|
| `/clear` | コンテキスト完全リセット | 無関係な別タスクへ移行時 |
| `/compact` | 自動圧縮（重要情報を保持） | 同一タスク継続・コンテキスト 60% 超時 |
| `/compact <instructions>` | 指定内容を保持して圧縮 | `"/compact Focus on API changes"` |
| `/btw <question>` | 会話履歴に残らない質問 | 作業中断せずに情報確認 |
| `/rewind` | チェックポイントに戻る | 誤った方向への修正後 |

#### CLAUDE.md にコンパクション指示を埋め込む

```markdown
<!-- CLAUDE.md -->
## Compaction Instructions
When compacting, always preserve:
- The full list of modified files with their purposes
- Any test commands that were run and their results
- Current sprint goal and task status
- Known blockers or decisions made
```

**適用提案**:
- 大規模変更は必ず 4 フェーズ（Explore → Plan → Implement → Commit）で進める
- タスク切り替えは `/clear` で徹底する（コンテキストノイズが最大の性能劣化要因）
- CLAUDE.md にコンパクション指示を埋め込み、圧縮後も重要情報が保持されるようにする
- 2回同じ修正をしても Claude が理解しない場合は `/clear` + より具体的なプロンプトで再開
